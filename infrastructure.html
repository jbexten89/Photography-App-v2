1. The Three Services at a Glance

The Photography Bookkeeping App is a static single-page web app with cloud sync. It runs on a three-service stack — each service has one job and they hand off to each other in predictable ways.

ServiceRoleWhat lives there
GitHubSource of truth for codeindex.html, app.js, styles.css, manual.html on the main branch of the v2 repo
VercelBuilds, hosts, and serves the app over HTTPSThe compiled static site at your public URL, served from a global CDN
SupabaseDatabase + authentication for cloud syncThe app_state_v2 table (one row per user) and the auth user account

Key insight: Vercel only ever sends static files. It never touches your data. Once the browser loads the app, the browser talks directly to Supabase. Vercel is not in the data path.

2. Deploy Flow — From git push to Live

Every time code is changed and pushed to main, the following sequence runs automatically. This is the only path that puts new code in front of users; there is no manual deploy step.

Diagram 2 — Deployment Pipeline (push → live, ~30–60 seconds)

What each step actually does

  1. Edit locally. All files are plain text. When changing app.js or styles.css, bump the cache buster query string (?v=NNN) in index.html so phones reload the new file instead of using a stale cached copy.
  2. Push to GitHub. The command git push v2 HEAD:main sends the commit to the v2 remote's main branch — GitHub stores it permanently and updates the branch pointer.
  3. GitHub fires a webhook. The repo has a webhook installed by Vercel during initial connection. On every push to main GitHub sends a POST request to Vercel containing the commit SHA.
  4. Vercel builds. Because the project has no package.json build step, Vercel simply copies the static files (HTML, JS, CSS, images) into its CDN. This takes seconds.
  5. Live worldwide. Vercel atomically swaps the production alias to the new deployment. The next HTTPS request from any browser gets the new files from the nearest edge location.
If Vercel misses a commit: push an empty commit to nudge it — git commit --allow-empty -m "nudge" && git push v2 HEAD:main.

3. Runtime — How the App Loads and Syncs

Once deployed, this is what happens every time the app is opened or used.

Diagram 3 — Runtime Request & Sync Flow

Step-by-step

  1. App load. The browser requests https://<your-domain>/. Vercel's nearest edge server returns index.html. The HTML pulls styles.css?v=NNN and app.js?v=NNN (the version query forces a fresh download whenever the number bumps).
  2. Local state hydrates first. app.js reads localStorage key photo-bookkeeping-v1 and immediately renders the UI from that cached state, so the app is usable offline and before any network call completes.
  3. Auth check. If a Supabase JWT is present in localStorage and still valid, the user is signed in. Otherwise the login screen is shown.
  4. Pull from Supabase. Once authenticated, the app queries app_state_v2 for the row matching the logged-in user's user_id. If the cloud copy is newer than local, it replaces local state and re-renders.
  5. Edits go to localStorage first. Every change (add transaction, edit invoice, mark trip) updates in-memory state, persists to localStorage immediately, and re-renders. This is instant — no network wait.
  6. Debounced push to Supabase. A short debounce (typically a few seconds of inactivity) triggers an upsert into app_state_v2 — the entire state blob is written as a single JSONB row. Other devices logged into the same account pick up the change on their next pull.

4. Why Three Services Instead of One

ConcernSolved byWhy not somewhere else
Version history, rollback, code reviewGitHubVercel keeps deploy history but the source of truth is the git tree
Free global HTTPS, instant cache invalidationVercelGitHub Pages would work but lacks the same edge speed and atomic swaps
User accounts & per-user data isolationSupabase Auth + Row Level SecurityVercel has no database; rolling your own auth is expensive and risky
Cross-device sync (phone ↔ laptop)Supabase Postgres (jsonb state column)localStorage is per-browser; Vercel doesn't store state
Offline-first behaviorlocalStorage in the browserGoing to Supabase first would block the UI when offline

5. Failure Modes & What Happens

If this breaks…What still worksWhat breaks
GitHub is down The live site keeps working. Existing users keep using it. You can't push new code or trigger deploys.
Vercel is down Already-loaded browser tabs keep working (the JS is cached). Local data is safe. New visitors can't load the site. The URL is unreachable.
Supabase is down App loads, localStorage data is intact, everything renders, edits are saved locally. Login fails (if not already signed in). No cloud sync. Other devices fall out of sync until it returns.
User is offline Everything except cloud sync. The app is fully usable on a plane. Changes don't propagate to other devices until the connection returns.
Cache-buster not bumped App loads with the old app.js / styles.css. Users see stale behavior until they hard-refresh.

6. Where Each Thing Lives

GitHub

  • Remote name: v2 · Branch: main
  • Tracked files: index.html, app.js, styles.css, manual.html, infrastructure.html, plus image/icon assets.
  • Every commit triggers a deploy. There are no protected branches or required reviews — push goes live.

Vercel

  • Project is linked to the GitHub repo's main branch.
  • No build command — it's a static site, files are served as-is.
  • Environment variables (Supabase URL and anon key) are embedded directly in app.js because the anon key is safe to expose publicly; security comes from Supabase Row Level Security policies.

Supabase

  • Auth: email + password. JWTs are stored in browser localStorage by the Supabase JS client.
  • Database table app_state_v2: 
    user_id     uuid       primary key, references auth.users(id)
state       jsonb      the entire app state blob
updated_at  timestamp  bumped on every upsert
  • Row Level Security: a policy restricts SELECT / UPDATE / INSERT on app_state_v2 to rows where user_id = auth.uid(). Even with the public anon key, one user cannot read another's row.

7. End-to-End Example — Adding a Feature

Suppose you add a new chart to the Analytics page. The full lifecycle:

  1. Open app.js, write the new render function and wire it to the menu.
  2. Open styles.css, add the chart's styles.
  3. Open index.html, bump ?v=143 → ?v=144 on both files.
  4. git add . && git commit -m "Add new chart" && git push v2 HEAD:main
  5. GitHub stores the commit and pings Vercel via webhook (within ~1 second).
  6. Vercel uploads the changed files to its CDN (~20–40 seconds).
  7. You hard-refresh on your phone. The browser sees ?v=144, downloads the new files, runs the new render function — the chart appears.
  8. You add a transaction. localStorage updates instantly. A few seconds later the debounced sync upserts the new state to app_state_v2 in Supabase.
  9. You open the app on your laptop. It pulls the latest row from app_state_v2, sees the new transaction, and renders it in the new chart.
That's the whole stack. GitHub holds the code, Vercel ships it, Supabase holds the data, and the browser does all the actual work — including formulas, rendering, filtering, and reports.
