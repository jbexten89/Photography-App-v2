1. The Big Picture

Your app uses three completely separate services, each owned by a different company. Each one has a single job:

ServiceWhat it doesWhat lives there
GitHub Stores the source code and tracks every change index.html, app.js, styles.css
Vercel Serves the website to anyone who visits the URL The compiled/deployed version of the same files
Supabase Stores YOUR data (transactions, jobs, invoices, etc.) and handles your login The app_state_v2 table + your user account

An analogy you might know

Imagine you're publishing a magazine.

  • GitHub is your filing cabinet — every draft, every edit, every revision is filed there.
  • Vercel is the printing press + delivery truck — it takes whatever's in the cabinet and gets a copy to readers.
  • Supabase is your customer database — it remembers each subscriber's info between issues.

Why three services?

You could build all this on one platform, but you'd lose the cleanest trade-off this stack offers: each service is the best at exactly one job. GitHub is best for code history. Vercel is best at instantly deploying static sites. Supabase is best at storing user data with proper security rules. They're built to talk to each other.

The best part

All three have free tiers that cover everything this app needs. Your monthly cost is $0 unless you outgrow them.

2. Architecture — The Whole System

Here's the complete picture: where the data flows, what runs where, and who talks to whom.

Reading the diagram

Top row is the code pipeline: you write code, push to GitHub, Vercel auto-deploys it. Bottom half is the runtime: a user opens the browser, downloads the app from Vercel, and uses Supabase to load + save their personal data.

Crucially, your data never goes through GitHub or Vercel. It travels directly from the browser to Supabase. GitHub and Vercel only see the public app code, never your transactions or jobs.

3. GitHub — The Code Vault

What it does

GitHub stores every version of your app's source code. Every change is a "commit" with a timestamp, a message, and a unique fingerprint. You can roll back to any prior version at any time.

Where your app lives

Your v2 code lives at: github.com/jbexten89/Photography-App-v2

The main branch is the "live" version. Whatever's on main is what Vercel deploys.

How code gets there

The three commands you'll use

git add app.js                # stage what you changed
git commit -m "Fix typo"      # save snapshot with a description
git push                      # send it to GitHub

Why version control matters here

  • Undo is free. Broke something three commits ago? Roll back in 10 seconds.
  • Vercel listens for pushes. Every push triggers an automatic deploy.
  • You can work from anywhere. Lost your laptop? Clone the repo on a new machine and you have everything back.

Two repos in your account

Photography — the v1 app (still running). Photography-App-v2 — this one. They're independent; pushing to one doesn't affect the other.

4. Vercel — The Hosting + Deploy Engine

What it does

Vercel takes the files on your GitHub repo's main branch and serves them at a URL anyone in the world can visit. It also auto-deploys — every time you push to GitHub, Vercel builds and publishes the new version, usually within 30–60 seconds. No manual upload step.

Your URL

https://photography-app-v2.vercel.app/

What a deploy looks like

Why Vercel and not just GitHub Pages?

  • Custom domain support — if you ever buy a real domain like photography.bexten.com, Vercel hooks it up in two clicks.
  • Better caching — files are served from a CDN closest to whoever's loading the page.
  • Built-in deploy protection — password gates, preview environments, instant rollback.

The CDN, briefly

A CDN (Content Delivery Network) is a network of servers around the world. When you visit your site, the files come from the server geographically closest to you, not from a single origin. That's why the app loads fast even on slow connections.

Caching gotcha

Sometimes your browser holds onto the old version of app.js even after Vercel deploys a new one. If you don't see your latest change, hard-refresh: Ctrl+F5 (Windows) or Cmd+Shift+R (Mac).

5. Supabase — The Data Vault

What it does

Supabase is a cloud database. It holds your data — transactions, jobs, invoices, customers, settings — and lets the app read and write to it from any device. It also handles your login (email + password authentication).

The table

Your data lives in a single PostgreSQL table called app_state_v2:

ColumnTypeWhat it is
user_idUUIDLinks the row to your login. Acts as the row's primary key.
dataJSONBThe entire app state — transactions, jobs, invoices, settings — as one giant JSON blob.
updated_attimestamptzWhen the row was last saved. Updated on every push.

One row per user

Every authenticated user gets exactly one row. Yours might look like:

user_id     | ed4e364b-b312-4660-a3fd-281bd...
data        | {"jobs":[...], "transactions":[...], ...}
updated_at  | 2026-05-04 21:46:06+00

Row Level Security (RLS) — how privacy actually works

The single most important Supabase feature for this app. RLS is a database rule that says:

"You can only read or write rows where the row's user_id equals YOUR user_id."

This is enforced by Postgres itself, not the app. Even if someone stole the public anon key embedded in app.js and crafted a malicious request, they still couldn't read your row without your password — because they wouldn't be authenticated as you, and RLS would refuse the query.

How saves work

This means: if Supabase is down or you're offline, the app still works. Your edits queue locally and push the next time the connection is up.

v1 vs v2 separation

v1 writes to app_state. v2 writes to app_state_v2. Same login, two separate tables, no risk of one overwriting the other.

6. End-to-End: How a Change Gets to You

Scenario A — You ship a code change

You fix a typo and want it on the live site.

  1. You edit app.js in your local copy.
  2. git add, git commit, git push — the change uploads to GitHub.
  3. GitHub fires a webhook to Vercel ("hey, new code on main").
  4. Vercel pulls the code, builds it (no actual build step here, it's static), copies to the CDN.
  5. Anyone visiting the URL now gets the new version.

Scenario B — A user adds a transaction

  1. You're on the live site. You click + New Transaction, fill it in, hit Save.
  2. The browser updates its local state and writes to localStorage — instant. UI updates immediately.
  3. The app calls supa.from("app_state_v2").upsert(state).
  4. Supabase verifies your auth token, applies the RLS policy, updates your row.
  5. Sync indicator in the sidebar flips ◐ Syncing → ● Synced.

Scenario C — You sign in from a new device

  1. Open the app URL in a fresh browser. Local storage is empty.
  2. Settings → Cloud Sync → enter email + password → Sign In.
  3. Supabase confirms the password and returns an auth token.
  4. App calls supa.from("app_state_v2").select() — pulls your row.
  5. App writes the JSON blob into local state and re-renders the entire UI. Your data is back.

Two distinct passwords (don't mix them up)

  • App access password — the gate that pops up when you first open the URL. Required so randos can't see the app shell. Hashed in app.js.
  • Supabase login (email + password) — what unlocks YOUR data inside the app. Required for cloud sync.

Different things. The app gate just gets you into the app interface. The Supabase login then loads your bookkeeping data.

If you forget the app gate password

Edit app.js line near the top: const APP_GATE_HASH = "..." — replace the hash, push to GitHub, Vercel auto-deploys, gate uses the new password.

If you forget your Supabase password

Use the Supabase dashboard to reset it (Authentication → Users → find your account → Reset Password). Or write a new password into your app login form — Supabase will email you a reset link.

8. Common Issues & Quick Fixes

"My code change isn't on the live site"

  1. Check Vercel Dashboard → Deployments. The most recent one should match your latest commit hash on GitHub.
  2. If it doesn't, the webhook is broken. Vercel → project Settings → Git → reconnect the repo.
  3. If the deploy says Ready but the page still looks old, hard-refresh (Ctrl+F5) — your browser is caching.

"Sync indicator says ● Error"

  1. Check internet connection.
  2. Open DevTools (F12) → Console tab — look for an error from Supabase.
  3. If error is "JWT expired", sign out + sign back in (Cloud Sync card → Sign Out, then Sign In).

"My data disappeared on a new device"

You haven't signed in yet on that device. Settings → Cloud Sync → Sign In with your email + password. The app will pull your row from Supabase and load everything.

"I deleted something by accident"

  1. If less than a few seconds ago, undo isn't built in — sorry.
  2. You have local backups in /Backups/. Settings → Backup & Import → Restore from Backup.
  3. Vercel doesn't help here — it has the code, not your data.
  4. Supabase doesn't keep automatic point-in-time backups on the free tier; on Pro it does.

"Vercel says deployment failed"

  1. Vercel Dashboard → the failed deploy → click "Build Logs" — the error message tells you what broke.
  2. Most common cause: a syntax error in app.js. Fix locally, commit, push.
  3. Old version stays live until the new build succeeds. No downtime.

"Site shows 403 Forbidden"

  1. Vercel → project Settings → Deployment Protection.
  2. If "Vercel Authentication" is on, disable it (or sign in to Vercel in this browser).
  3. If "Password Protection" is on (Pro plan), enter the password.

9. Glossary

Code & Git

Repo (repository)A collection of related code files tracked together. Your app is one repo.
CommitA snapshot of your code at a moment in time, with a message describing what changed.
BranchA parallel line of commits. main is the official one. You can create others to experiment without affecting the live site.
PushUpload your local commits to GitHub.
PullDownload the latest commits from GitHub to your local copy.

Hosting & the Web

DeployThe act of taking code and making it live on a URL.
CDNContent Delivery Network — a network of servers worldwide that serve files quickly to nearby users.
WebhookAn automatic message one service sends to another when something happens. GitHub fires one to Vercel on every push.
localStorageA small storage area in your browser where the app saves data instantly so it survives page refreshes. Lives only on that device.

Database

SQLThe language used to ask the database for data ("get me all rows where x = 5").
JSONBA column type that stores arbitrary JSON. Your entire app state lives in one JSONB column.
RLSRow Level Security — rules baked into the database that decide which rows each user can see.
Auth token / JWTA digital pass the app sends with every request to prove you're you. Issued when you sign in, expires after a while.
Anon keyA public key embedded in app.js that says "I'm an anonymous app talking to Supabase." It only allows what RLS permits.
